    Batching: serving a GPT to many users at once

    We serve the model as an API in the shape of OpenAI's completions, measure it against a crowd of players from a game, write the stories for the requests that arrive together as a batch, and run it in Docker, with vLLM as the alternative.

    Watch on YouTube

    In this episode, we serve our model to many users at once, say the players of a game like nanoMMO from my other series, through an API in the shape of OpenAI's completions. Written one request at a time, the wait grows with the queue, so the server writes the stories of the waiting requests together, as a batch padded on the left. We measure it with a script that simulates a crowd of players, put the server in Docker, and look at vLLM as the alternative.

    vLLM

    22:43 Our batches start together and end together, so a row that finishes early keeps running, with its tokens dropped, until the last one is done. And a request that arrives just after a batch starts waits for all of it. Servers built for language models schedule each step instead, which is called continuous batching: a finished row leaves straight away, and a waiting request takes its place. vLLM, which started at UC Berkeley, does that, and it keeps the KV cache in blocks of a fixed size, which it calls PagedAttention, so that sequences of different lengths share the GPU's memory without padding. It runs on the CPU too, on x86, with AVX-512 or with fewer features on AVX2, and on ARM, and it has Docker images for the CPU. It loads both kinds of model we have on the Hub, the fine-tuned GPT-2 from episode three and the GPT-NeoX from episode twelve, and it serves OpenAI's completions API on port eight thousand, as ours does, so a client written for one works with the other.
